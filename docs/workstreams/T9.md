# T9: Security, Privacy & Abuse Prevention

Owner expertise: Security Engineering. No individual assignment implied.

## Research question

Threat-model Discord iframe, OAuth, tenant isolation, authoritative edits and public VPS attack surface; prioritize abuse scenarios.

## Required contract

Specify security controls, privacy inventory, retention/deletion policy, audit integrity and release security evidence.

## Capability scope

### Identity and tenant security

- **OAuth, sessions and credential handling**: Review code exchange, replay, session fixation, token exposure and secret rotation; validate CSRF/origin controls appropriate to chosen auth transport; prohibit secrets in source, logs and exports.

- **Privilege escalation and tenant isolation**: Prove route/socket/object authorization denies foreign guild identifiers, forged roles, stale grants and moderator-to-admin escalation; add negative test for each critical boundary.

### Content and input defenses

- **XSS, SQL injection and path traversal**: Validate and parameterize database input; sanitize imported text/URLs; prohibit arbitrary filesystem paths and unsafe rendering; define and test Discord-compatible content security policy.

- **Upload and resource abuse protection**: Enforce decoded file limits, content type checks, quotas and safe storage; test polyglots, oversized payloads, decompression bombs, message floods and slow clients.

### Privacy and audit

- **Retention, deletion and privacy disclosure**: Inventory Discord identifiers, board content, assets, logs and backups; define purpose/access/retention; implement deletion propagation and explain backup retention exceptions.

- **Audit integrity and incident evidence**: Protect audit records from ordinary writers and moderators; record security events without tokens or unnecessary content; define access control, integrity checks and evidence preservation.

### Security assurance

- **Dependency auditing and security automation**: Run dependency, secret and static analysis checks with triaged findings; record exceptions with expiry conditions; verify lockfile provenance and license obligations.

- **Independent security review and release gate**: Obtain an actual independent review of auth, tenancy, imports, replay and VPS exposure; remediate findings and retain evidence; block release on unresolved critical/high risk without accepted disposition.

### GB-T9.04.01.T1 local supply-chain verifier

[#317](https://github.com/CompleteTech-DiscordApps/guildboard/issues/317) adds an
offline verifier for the committed Git `HEAD`. Run it from the repository root
using the verifier from that revision. It inventories the root and isolated canvas
npm lockfiles and their committed manifests, checks workspace links and canonical
npm registry tarball URLs and SRI, and reuses the existing offline license gate
with both lockfiles and the committed policy data. The canvas license exceptions
remain scoped to research under the existing policy. Inspecting SRI syntax proves
the shape of a pin. Independent provenance evidence is required to establish
that the lock can be reproduced and its artifact digests match.

```sh
python3 -B scripts/verification/check_t9_supply_chain.py
python3 -B scripts/verification/check_t9_supply_chain.py --trusted-authority-sha256 "$APPROVED_AUTHORITY_SHA256"
python3 -B -m unittest discover -s tests/verification -p 'test_t9*.py' -v
```

Use the first command for a local baseline. In the second command the SHA-256
must come directly from a protected channel controlled by a designated independent
Security Engineering reviewer. The reviewer confirms that each tool and profile is
approved for its exact scope and that the named producer, job and artifact match
the source revision, redacted result and finding dispositions. The reviewer also
verifies each exception's authority and controls. A locally calculated digest of
someone else's bundle cannot authorize it. The CLI compares the protected digest
to exact authority-file bytes and follows the verified hashes from that file. It
does not fetch or authenticate the channel itself.

Use an ephemeral checkout and place only the redacted JSON records below in
`.t9-assurance/` at its root. Keep the directory out of commits. Each record is
at most 256 KiB, and all field sets are closed. Every record carries
`version` (integer 1), `repository` (`CompleteTech-DiscordApps/guildboard`) and
`revision` (full lowercase Git `HEAD`). Dates use `YYYY-MM-DDTHH:MM:SSZ` UTC.
Digests and opaque references are 64 lowercase hexadecimal characters. Use
opaque references assigned by the evidence producer or evidence custodian.
Only approved source and redacted artifacts belong in this interface. Never
copy credentials, private package material, scanner snippets, repository-external
paths, or raw scanner output into these records or the command line.

| File | Additional required fields |
| --- | --- |
| `authority.json` | `reviewer`, `issued_at`, `expires_at`, `approvals_sha256`, `receipts`. The receipt map keys are the six receipt basenames below (without `.json`). Each value contains exactly `producer`, `tool_sha256`, `profile_sha256`, `receipt_sha256`. SHA-256 hash fields cover exact bytes. |
| `provenance-root.json`, `provenance-canvas.json` | Common receipt fields, `lock_sha256`, `manifest_set_sha256`. The exact result value is `reproduced-and-integrity-verified`. |
| `dependency-root.json`, `dependency-canvas.json` | Common receipt fields, `lock_sha256`, `manifest_set_sha256`, `findings`. |
| `secret-source.json`, `static-source.json` | Common receipt fields, `findings`. |
| `approvals.json` | `reviewer`, `exceptions`. Each exception carries `receipt_sha256`, `finding_id`, `severity`, `approved_at`, `expires_at`, `decision` (`temporary-exception`), `reason` (`mitigation-verified` or `false-positive-verified`), one to eight unique digest references in `controls`, and `closure_criteria_sha256`. Use an empty array if no finding has a disposition. |

Common receipt fields are `kind`, `scope`, `producer`, `tool_sha256`,
`profile_sha256`, `completed_at`, `run_id`, `artifact_sha256` and `result`.
Use the basename's kind and scope, a distinct job/step reference for each run,
and the digest of the exact access-controlled source artifact used for review.
For each npm scope, `manifest_set_sha256` hashes the concatenated ASCII hex
SHA-256 values of the committed manifest bytes in the verifier's `MANIFESTS`
order, root manifest first. The lock hash covers the exact committed lockfile.
A scanner result is `clear` with an empty findings array or `findings` with up
to 512 distinct entries. Each finding has an opaque `id` and a `severity` of
`low`, `moderate`, `high` or `critical`. Every finding needs an exact disposition.
Approval references bind the finding to the exact receipt digest and severity.
The reviewer must differ from every producer. Scans must be at most seven days
old and completed before or at authority issuance. Authority expires within
seven days of issuance. Each approval must follow the scan and expire within
30 days of approval. Authority and exception expiry are exclusive.

Exit `0` is a pass for this supply-chain check. Exit `1` means a policy failure
or unresolved finding. Exit `2` means the result remains unverified because
source, evidence or authority was missing or invalid. Findings and details
remain with the authorized custodian. Historical reports always have the
`HISTORICAL_ONLY` classification. The archived root report still informs
[#458](https://github.com/CompleteTech-DiscordApps/guildboard/issues/458).
The known root pin retains a hold unless the narrowly reviewed withdrawal below
matches. Clear scanner receipts alone cannot remove that hold. The offline
checker reports a dated disposition or unknown current status, never live issue
state inferred from a package name.
