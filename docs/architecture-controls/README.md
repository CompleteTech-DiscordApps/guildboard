# Architecture change gate, version 1

`python3 scripts/architecture-controls/check.py --base /path/to/reviewed-base --current /path/to/proposed-tree` compares explicit trees without Git or network. It validates each tree's baseline against actual bytes, checks the head trace against accepted canonical fixtures, and requires an exact old/new SHA-256 decision record for every added, removed or changed boundary. Renames are a removal and an addition. Boundary inputs are the critical documents listed in the checker and all regular files under apps, packages, database and infra/godaddy. Missing roots, symlinks, oversized files, malformed JSON and unknown record shapes fail closed. There is no writer, automatic reseal or artifact promotion.

For a change, prepare a new baseline reflecting the proposed bytes and an entry in `decisions.json` with a unique decision ID, positive revision, exact path and old/new hashes (null for absent), rationale, alternatives, and existing control and test evidence paths. Record what reviewers must assess; existence and hashes do not establish adequacy or execution. A reviewer must read the actual semantic diff, rationale, alternatives and evidence, including downstream impacts; actual review and protected merge are required before the proposed baseline becomes the reviewed base. Do not update accepted identity pins without their own review and acceptance process. Historical records remain versioned; a record only covers the exact hashes it names.

The PR workflow runs the base checker and base tests for ordinary changes. For the first installation only, when the base has no gate, it runs the proposed checker and tests with `--bootstrap-base-sha`; this mode accepts only the explicitly pinned GitHub base SHA and the complete boundary witness in `bootstrap.json`. The manifest records a requirement for independent review and protected merge; it is not evidence that either occurred. The checker validates the initial head baseline, traceability and decision records against the witnessed base, including the new threat model. If main changes, the owner must explicitly reconcile the base SHA, boundary witness and review; do not silently reseal. Once installed, a missing checker on any later base fails closed.

The first-install workflow, checker and manifest come from the proposed head, so an adversarial head can alter or bypass their logic. The pinned witness is useful only after independent reviewers verify it against the actual base and review all initial policy and workflow bytes. A mechanical pass cannot establish that review or protect the workflow itself; native CI, independent review and protected merge remain required. Base SHA and head SHA come from the pull request event, not its title.

Traceability links canonical requirements and fixture IDs to named interfaces and design controls with evidence paths. The fixtures are declarative, and the gate cannot prove prose semantics or product behavior.
