# GitHub bootstrap and reconciliation

Run from this repository using Python 3.11+ and authenticated `gh`. Never put tokens in the manifest or command output. Destination is pinned in `planning/github-state.json`; the reference Project is read-only and no script mutates it.

`validate.py` and its tests are offline exceptions: they require only Python's standard library, not `gh`, authentication, network access, application architecture decisions, or a GoDaddy deployment. Run `python3 -m unittest discover -s tests/planning -v` before changing the validator. Planning CI runs this regression suite before checking the manifest.

The validator always exits nonzero for invalid input and prints a JSON failure report. Missing references, malformed input, duplicate JSON keys, hierarchy/blocker cycles, and empty manifests produce diagnostics rather than uncaught graph traversal exceptions. When the report destination is writable, failure replaces any previous report atomically; a report-write failure also exits nonzero and is reported on stdout. Each invocation stages its own temporary file in the destination directory. A report path that aliases a validation input (including symlinks and hardlinks) is rejected without overwriting either input. The validator pins the report directory through a POSIX descriptor or Windows directory handle and compares file identities relative to it. It fails closed if the required operations or identities are unavailable, or an input cannot be inspected; in that case an existing report is not replaced. On POSIX systems without `O_PATH`, opening the directory may require read permission. Windows uses native handle-relative creation and `FileRenameInformationEx` replacement (Windows 10 version 1803 or later), with `REPLACE_IF_EXISTS | POSIX_SEMANTICS` so an earlier publisher can retain its old report handle while a successor publishes. Existing handles still refer to the previous file; new opens see the replacement. The pinned directory's `FileCaseSensitiveInfo` must also be available: ordinary Windows directories use one case-folded lookup, while case-sensitive directories retain the exact/folded ambiguity guard. Query failure or unknown flags fail closed. Unsupported operating systems or filesystems fail closed without a pathname fallback. See Microsoft's [rename flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) and [information-class support](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_file_information_class). If Windows denies cleanup after a failed publication, the cleanup failure is reported and the randomly named stage file may remain in the report directory. Keep input paths, report directory entries and directory case-sensitivity settings stable during validation: concurrent changes to those entries are outside the source-preservation guarantee. Never interpret an old report file as evidence when the command failed to write its current result. Graph traversal is iterative, so deep invalid chains do not depend on Python's recursion limit.

By default, validation reads `planning/guildboard-backlog.json` and `planning/project-schema.json`, checks the repository identity in `planning/github-state.json` and generated reports, and writes `planning/audit/local-validation.json`. Test fixtures can use `--manifest PATH --schema PATH --report PATH` without changing repository inputs. Use `--state PATH` and repeatable `--generated PATH` to check repository identity with fixture files. Validation does not modify the manifest, infer completion of native blockers, or reconcile live Project fields. A passing report is planning-structure evidence only, not product, Discord, concurrency, security, or VPS acceptance.

## Canonical sources

`planning/workstreams.json` contains authored capability requirements. `generate.py` compiles stable work units into `planning/guildboard-backlog.json`, preserving existing remote mappings. Project fields are live execution authority; the manifest records initial planning intent. Do not regenerate during a concurrent reconciliation process.

## Execution

For a missing initial state, `initialize.py` resolves the authorized viewer and current reference ID, detects existing entities, and copies configuration with no draft items. Existing state pins this destination; initialization never publishes an existing private repository or silently replaces an unavailable Project. Then use `configure.py`/`views.py` only for deliberate schema administration.

1. `python3 scripts/github-bootstrap/validate.py`
2. `python3 scripts/github-bootstrap/reconcile.py --phase issues`
3. `python3 scripts/github-bootstrap/reconcile.py --phase links`
4. `python3 scripts/github-bootstrap/reconcile.py --phase fields`
5. `python3 scripts/github-bootstrap/reconcile.py --phase comments`
6. `python3 scripts/github-bootstrap/reconcile_dependency_status.py`
7. `python3 scripts/github-bootstrap/repair_visible_blockers.py`
8. `python3 scripts/github-bootstrap/reports.py`
9. `python3 scripts/github-bootstrap/repair_repository_metadata.py`
10. `python3 scripts/github-bootstrap/audit.py`

Use `reconcile.py --verify-only` for independent readback. Use `reconcile.py --phase comments --dry-run` to count candidate body rewrites without writing local files or updating GitHub. Failed reads and issue identity mismatches exit with a generic diagnostic. The preview uses the stored issue number and node ID to verify each stable marker. It reports which candidate rewrites would change more than transfer-era repository links and skips maintainer-edited bodies, including issues with removed stable markers. Initial bootstrap acceptance uses `audit.py --strict-initial`; ordinary audit records legitimate execution-field drift as informational while still failing missing/contradictory metadata. `repair_repository_metadata.py` fills missing labels/milestones and preserves existing milestone changes unless explicitly invoked with `--apply-planned-milestones`. `configure.py` and `views.py` are explicit schema-administration commands; they intentionally reconcile the declared schema/view definitions and should not be run casually after maintainers customize them.

Every issue is detected by durable body marker before creation. Before a failed create is retried, restart the phase to refresh markers, preventing duplication after uncertain transport outcomes. Writes are paced; rate limits back off. Failures log to ignored `planning/audit/failures.jsonl`; review/redact before sharing. Stable mappings persist atomically after every successful creation. Native hierarchy/dependencies are read before repair; a conflicting existing parent aborts instead of replacing legitimate work. Field reconciliation fills missing fields and preserves existing changes after initial triage. Deliberate field drift is reported for review rather than reset. Reruns do not reassign contributors, close issues or repeat marked handoff comments.

## UI-only configuration

GitHub's current public GraphQL view API configures names, layouts, filters and visible fields. Grouping, hierarchy display, roadmap axes, Insights and workflow trigger/action settings are handled in the authorized UI and independently captured in audit artifacts. Inspect the saved settings after changes; URL-only display options are not sufficient proof.

Native auto-add enrolls new Guildboard issues, sub-issue enrollment stays enabled, intake/reopened work returns to Triage, closed work maps to Done, linked PRs map to In Progress and merged PR items map to Done. Automatic issue closure on Project Done is disabled; a status edit is not acceptance evidence. No workflow sets Verification Status to Verified.

## Integrity automation

Repository CI validates manifest identity, metadata, hierarchy limits and dependency cycles. The repository integrity workflow detects missing issue-body criteria, missing milestones/labels, unexpected parent/dependency links and parent closure inconsistency using its restricted repository token. Authenticated `audit.py` additionally checks actual Project field values, enrollment, views, schema and repository association. A scoped `GUILDBOARD_PROJECT_TOKEN` secret can enable that full scheduled audit; the bootstrap does not silently copy a broad personal OAuth token into a public repository's Actions secrets.

New community issues are intentionally untriaged until maintainers supply valid scope and Project metadata. Unassigned work remains visible and is not an error by itself. Review audit JSON findings; never interpret workflow execution alone as application verification.

For an issue reviewed as outside the canonical roadmap, maintainers record its issue number, disposition kind, and reason in `planning/repository-issue-dispositions.json` through the ordinary PR review process. The repository audit accepts `resolved_incident` only for a closed issue. It accepts `campaign_tracking` while the tracker is open or after it closes. Successful entries are listed under `reviewed_dispositions` with their observed state. The audit fails for unclassified issues, missing disposition targets, state mismatches and disposition targets carrying a roadmap marker. If work moves onto the canonical roadmap, remove its disposition and complete the normal roadmap metadata.
